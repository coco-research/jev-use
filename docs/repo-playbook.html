The Repo Standard

Every repository you own carries the same skeleton, the same gate and the same six documents. This is the instruction set: an agent reads it once and can bring any repo into compliance without asking.

Revision 2 — 2026-09-20. Checked by scripts/repo-check, which is the tool, not a description of one. This file lists the checks it runs; the tool fails when that list and reality disagree, so the document cannot rot quietly. Section 7 has the change log.

0How to use this document

Read this section before the rest. It tells you what to do, in order.

  1. Audit first. repo-check --repo <path> reports exactly what is missing. Do not guess, and do not work from memory of this page.
  2. Fix tier 1 before anything else. Tier 1 is mandatory for every repo: no exceptions, no judgement calls.
  3. Copy, do not invent. Every tier-1 file has a working example in a repo that is already compliant. Start there and adjust the content.
  4. Re-run the audit. It must say COMPLIANT before the job is done — not "mostly", not "except for".
  5. Never delete a document to make the audit pass. A stub is treated as a failure on purpose: an empty placeholder is worse than a missing file.

The one rule under all the others: a document that lies is worse than no document, because the next agent will act on it. If a change makes a document wrong, fix the document in the same commit — including this one.

1The twelve standing rules

Not stylistic. Each exists because its absence caused a specific, observed failure.

01
Every repo has an AGENTS.md at root, under 160 lines. It is the one file an agent reads first. Not rules — a map: where the documents are, which one wins when they disagree, what to read first. Five of seven repos were missing it, so every agent started from zero.
02
Work lands through a small PR. Nothing is pushed straight to main. A PR is where a change becomes explainable. A commit on main is where it becomes anonymous.
03
A gate runs before every push, and it is local. CI can be refused — a private repo on an exhausted budget was, outright — and a hosted runner cannot test anything that needs a GUI session. The hook cannot be refused. It must also be fast: a gate that costs twelve seconds is a gate that gets --no-verify within a day, and a bypassed gate protects nothing.
04
Evidence, never assertion, in the PR body. "Tests pass" is a claim. The command and its real output is a fact. Every section of the PR template exists to force the second.
05
One owner per fact. Two documents must never both be authoritative for the same thing. Two sources of truth is a bug that reads as documentation.
06
An invariant is written with the measurement behind it. "Set the messaging timeout" is an opinion and gets removed. "Without this timeout the call hangs rather than fails; measured on PI-Desktop returning CannotComplete" is a fact and survives review.
07
Dead ends are recorded, not deleted. The cheapest and most-skipped thing in any repo. One sentence — "we tried X, it failed because Y" — saves the next agent the hour you already spent. The wrong diagnoses are worth more than the right one: they are the ones someone will have again.
08
No credential reaches a tracked file, a log, a response body or a commit message. Read secrets by path at runtime; never copy one in, not even to debug. If one lands: remove it, rotate it, and say so — assume it is already public. Fake fixtures must be obviously fake (sk-test-…).
09
A public repo asks for the reader's keys, never carries ours. Anything published ships with no provider list, no wallet topology and no absolute home path. It must behave like a fresh install and ask, rather than quietly running on the author's credentials. Absolute machine paths in shipped code are the same mistake in a different costume.
10
One checkout per repository. Two working copies of one repo is how two agents end up editing different versions of the same file, and this machine has the scars. If a second copy exists, that is a bug — say so and delete it. A mirror that must exist (a products folder, a runner's work directory) is a clone with an origin, not a hand copy.
11
Documents and the machine-readable gate must agree. Three documents called themselves "draft, awaiting approval" while GATE.json recorded them approved. Both were readable; only one was true. When they disagree, fix the disagreement in the same commit — and prefer the state file as the record of approval, because that is the one the workflow reads.
12
A doc that nothing checks is a doc that rots. This page was three weeks stale and nothing noticed, because repo-check examined the six Markdown documents and no HTML. So this file declares the checks it documents, and the tool fails when the two lists differ. If you add a check, you update this page in the same commit.

3The gate is three layers, and each one sees something the others cannot

This is the part most often got wrong. They are not redundant.

LayerScansCatchesCannot catch
pre-push hook
fast, local		 the staged diff a key as it is being typed; broken tests; formatting anything already committed three commits ago
repo-check
in the hook, and by hand		 tracked files a credential already in history; missing documents; a stale SoT what is not committed yet
CI
the backstop		 a clean checkout what a fresh clone breaks on — including a machine the author never used anything needing a GUI session, unless a self-hosted runner exists

Change detection, or the gate gets bypassed. Run the expensive checks only when the language they cover changed. A docs-only commit should pass in well under a second; a change to Python should run the suite. Change detection is safe here because anything that can break a test is a source change — a fixture is a source file.

A missing tool is an environment problem, not a code problem. The hook warns and continues rather than failing the push, because blaming the author for a broken toolchain is how a gate loses its authority. CI is the backstop for the check that could not run.

4The documents, and which one wins

Seven files, one authority order. When two disagree, the earlier one wins — and the disagreement is fixed in the same commit, never silently resolved.

6Templates, so the answer is never "write one from scratch"

Copy from a compliant repo rather than inventing. The files that have a house style:

  • .githooks/pre-push — the check runner, the time budget, the change detection and the credentials scan. Adapt the language-specific parts; keep the structure, the pass/warn/FAIL vocabulary and the reasoning in the comments.
  • .github/pull_request_template.md — what changed, the exact commands run, risk, rollback, and a checklist that includes "no key or secret is in this diff".
  • CONTRIBUTING.md — the loop, branch naming, commit format, PR size, and a definition of done.
  • .metagpt/GATE.json — the machine-readable state, including the approved decisions in the owner's words. It is the file the workflow reads, so it wins over prose.
  • AGENTS.md — the map: the documents table, the authority order, the repo's hard rules, and how to record what you learned.

7Change log — what Revision 2 fixed

Recorded because a standard that does not say what changed is a standard nobody can trust to be current.

  • Audited both repos against the standard, for the first time. keydeck was failing twelve checks — 2/6 required, 0/8 documents — while being a working, shipped application. A repo can be correct and unmaintainable at the same time; that is what the standard exists to catch.
  • jev-use passed the tool and failed the intent. Three documents called themselves "draft, awaiting owner approval" while GATE.json recorded them approved. Both were readable; one was false. → rule 11.
  • The gate gained repo-check as its second scan, so a credential committed earlier is caught on the next push rather than never.
  • Change detection replaced "always run the suite" in a Python repo's hook: a docs-only commit now passes in 0.37 s instead of 12 s. The reasoning that had justified the slow version contained an error — a fixture change is a source change, so detection cannot miss it.
  • Rules 9 and 10 are new. A public repo brings its own keys; one checkout per repository. Both came from incidents on this machine rather than from theory.
  • Rule 12, and this document's own meta tag. The playbook was three weeks stale because nothing examined it. Now the tool compares its check list against the list declared at the top of this page, and fails on a mismatch.
