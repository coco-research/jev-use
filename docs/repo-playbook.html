The Repo Standard

Every repository here carries the same skeleton, the same gate and the same documents. This is the instruction set: read it once and you can bring any repo into compliance without asking anyone.

Revision 5 — 2026-09-20. This exact file is deployed into every repository and every copy is byte-identical. It is general on purpose: if a rule only makes sense for one project, that rule belongs in that project's docs/rules.md, not here. Enforced by scripts/repo-check and kept identical by scripts/standard-sync.

0If you are an agent, start here

Five steps. They work on a repo you have never seen.

  1. Run the audit. python3 scripts/repo-check (or repo-check --repo <path>) reports exactly what is missing. Do not work from memory of this page, and do not guess.
  2. Read the repo's own documents in this order: AGENTS.md, docs/prd.md, docs/architecture.md, docs/rules.md, docs/tasks.md, docs/memory.md, .metagpt/STATE.md. That order is the authority order — when two disagree, the earlier one wins.
  3. Find the repo's own rules. docs/rules.md holds the invariants, each with the measurement behind it. Those are local laws on top of the standing rules below. If a task appears to require breaking one, stop and ask.
  4. Do the work through a small PR, with the command you ran and its real output in the body. Never push to main.
  5. Re-run the audit before claiming anything is done. It must say COMPLIANT. Not "mostly", not "except for".

The rule under all the others: a document that lies is worse than no document, because the next agent will act on it. If your change makes a document wrong, fix that document in the same commit — including this one.

1The twelve standing rules

Not stylistic. Each exists because its absence caused a specific, observed failure. They apply to every repository, regardless of language or purpose.

01
Every repo has an AGENTS.md at root, under 160 lines. It is the one file an agent reads first. Not rules — a map: where the documents are, which one wins when they disagree, what to read first. When it was missing, every agent started from zero and re-derived the project's shape by accident.
02
Work lands through a small PR. Nothing is pushed straight to main. A PR is where a change becomes explainable. A commit on main is where it becomes anonymous. Where a repo enforces review, do not bypass it — least of all with an admin flag.
03
A gate runs before every push, and it is local. CI can be refused (a private repo on an exhausted budget was), and a hosted runner cannot test anything needing a GUI session. The hook cannot be refused — but it must be fast. A gate that costs twelve seconds gets --no-verify within a day, and a bypassed gate protects nothing.
04
Evidence, never assertion, in the PR body. "Tests pass" is a claim. The command and its real output is a fact. Every section of the PR template exists to force the second. The same applies to a completion report: a claim without a measurement is an opinion wearing a uniform.
05
One owner per fact. Two documents must never both be authoritative for the same thing. Two sources of truth is a bug that reads as documentation. Where ownership is split between people or agents, the boundary is written down and crossing it means asking.
06
An invariant is written with the measurement behind it. "Set the messaging timeout" is an opinion and gets removed. "Without this timeout the call hangs rather than fails, measured on CannotComplete" is a fact and survives review. A rule without evidence is a preference, and preferences lose arguments.
07
Dead ends are recorded, not deleted. One sentence — "we tried X, it failed because Y" — saves the next agent the hour you spent. The wrong diagnoses are worth more than the right one: they are the ones someone will have again.
08
No credential reaches a tracked file, a log, a response body or a commit message. Read secrets by path at runtime; never copy one in, not even to debug. If one lands: remove it, rotate it, and say so — assume it is already public. Test fixtures must be obviously fake (sk-test-…) so the pattern to follow does not look like a leak.
09
A public repo asks for the reader's keys, never carries ours. Anything published ships with no provider list, no wallet topology and no absolute home path. It must behave like a fresh install and ask, rather than quietly running on the author's credentials. Absolute machine paths in shipped code are the same mistake in a different costume.
10
One checkout per repository. Two working copies of one repo is how two agents end up editing different versions of the same file. If a second copy exists, that is a bug — say so and remove it. A copy that must exist (a deployment folder, a runner's work directory, an intentional worktree) is a clone with an origin, never a hand-made duplicate.
11
Documents and the machine-readable state must agree. Documents once called themselves "draft, awaiting approval" while the state file recorded them approved. Both were readable; only one was true, and the workflow reads the state file. When they disagree, fix it in the same commit, and treat the state file as the record of what was actually decided.
12
A document nothing checks is a document that rots. This playbook itself sat three weeks stale and nothing noticed, because the checker examined the Markdown documents and no HTML. That is why it declares the checks it documents — and why every copy is compared against the canonical one. If you add, rename or remove a check, update this file in the same commit.

3The gate has three layers, and each sees something the others cannot

This is the part most often got wrong. They are not redundant, and none of them is optional.

LayerScansCatchesCannot catch
pre-push hook
fast, local		 the staged diff a key as it is being typed; broken tests; formatting anything already committed three commits ago
repo-check
in the hook, and by hand		 tracked files a credential already in history; missing documents; a stale standard what is not committed yet
CI
the backstop		 a clean checkout what a fresh clone breaks on — including a machine the author never used anything needing a GUI session, unless a self-hosted runner exists

Change detection, or the gate gets bypassed. Run the expensive checks only when the language they cover changed. A docs-only commit should pass in well under a second; a change to source should run the suite. Detection is safe because anything that can break a test is a source change — a fixture is a source file.

A missing tool is an environment problem, not a code problem. The hook warns and continues rather than failing the push: blaming the author for a broken toolchain is how a gate loses its authority. CI is the backstop for the check that could not run.

Never make a skipped check report as a pass. A test that could not look must say so, in the output and in the PR. A skipped test reported as green buys confidence it never earned, which is worse than having no test at all.

5Templates, so the answer is never "write one from scratch"

Copy from a repo that is already compliant, then adjust the content. The files with a house style, and what to preserve in each:

  • .githooks/pre-push — the check runner, a per-check time budget, change detection, and the credentials scan. Adapt the language-specific parts; keep the structure, the pass/warn/FAIL vocabulary, and the reasoning in the comments. The comments are the part that stops the next person from "simplifying" it back into a gate people bypass.
  • .github/pull_request_template.md — what changed, the exact commands run and their results, risk and blast radius, rollback, and a checklist including "no key or secret is in this diff".
  • CONTRIBUTING.md — the loop, branch naming, commit format, PR size, and a definition of done that includes running the gate.
  • .metagpt/GATE.json — machine-readable state, including the approved decisions in the owner's words. It is what the workflow reads, so it wins over prose.
  • AGENTS.md — the map: the documents table, the authority order, the repo's own hard rules, and how to record what you learned. Under 160 lines: it is a routing table, not an essay.
  • docs/memory.md — decisions with reasons, and dead ends. The most valuable entries are the wrong turns, written down while they are still embarrassing.

6How this file stays the same everywhere

A standard that exists in twenty folders with twenty slightly different texts is not a standard — it is twenty opinions. So the copies are mechanically kept identical.

CommandDoes
scripts/standard-sync --checkCompares every repository's copy against the canonical one and lists any that differ. Exit 1 on drift.
scripts/standard-sync --writeRedeploys the canonical file into every repository, creating docs/ where needed.
python3 scripts/repo-checkConfirms the file declares the checks the tool actually runs.

The canonical copy lives in products/jev-use/docs/repo-playbook.html. To change the standard: edit the canonical, bump the revision in the meta tags, run standard-sync --write, then --check to prove every copy matches. Editing a copy anywhere else is a bug — it will be overwritten, and it will have confused somebody before that happens.

Each copy also declares which checker belongs with it: repo-standard-checker-sha256-16 holds the hash of scripts/repo-check at this revision, and repo-standard-checker-revision names that revision. A repo whose local checker does not hash to that value is behind the standard, and its gate can say so instead of guessing.

standard-sync --write refuses two things, both learned by running it rather than reading it: it will not deploy a playbook that declares no revision, and it will not write into a repository that has uncommitted work. It reports those instead of burying somebody's in-flight changes behind one more modified file.

7What each repo adds on top

This file is the floor, not the ceiling. A repository's own docs/rules.md carries the invariants specific to it — the measurements that only matter there. Read this file to understand the shape; read the repo's rules before you touch its code.

Examples of the kind of thing that belongs in a repo's own rules and never here: a required parity target with a reference implementation, a security guard in a CI job that must not be removed, a two-tier verification rule where only one tier may report success, a UI contract, a licensing constraint. If you can imagine another repo needing the same sentence, it belongs in this file instead.

8Change log

A standard that does not say what changed is a standard nobody can trust to be current.

  • Revision 1 — the ten original rules, the three tiers, and the checker. Written after scanning seven repositories; agents were starting from zero in five of them.
  • Revision 2 (2026-09-20) — audited real repos against it for the first time and found both failure modes: one repo failing twelve checks while being a working application, and another passing the tool while three of its documents contradicted the state file. Added the one-checkout rule, the bring-your-own-keys rule, and rule 12 — a document nothing checks is a document that rots.
  • Revision 3 (2026-09-20) — made general, and deployed into every repository under products/ so an agent never has to find it. Added the standard-sync tool and the canonical-copy meta tag, because twenty copies of a standard are not a standard. Section 0 is new: the five steps an agent follows on a repo it has never seen.
  • Revision 4 (2026-09-20) — two defects in the standard itself, both found by running it rather than reading it. Rule 12 says this file declares the checks it documents, and the prose said nineteen while the meta tag declared twenty: nothing compared the two, so the count had drifted. And repo-check named the credentials outside test/evidence check only when it found something, so the self-check read that name as undocumented and failed any repo holding a single fixture-shaped key. The check now names itself either way, it is declared, and the count is correct.
  • Revision 5 (2026-09-20) — the file now says which checker goes with it, so a repo can tell whether its own scripts/repo-check is behind. Two refusals were added to standard-sync after running it against the real fleet instead of reading it: it will not deploy a playbook that declares no revision (a stale checkout would otherwise overwrite every good copy), and it will not write into a repo with uncommitted work. It also stopped counting directories that are not repositories — measured before the fix, 31 targets of which 24 were repositories, one of them completely empty.
